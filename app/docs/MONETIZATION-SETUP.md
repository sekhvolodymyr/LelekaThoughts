# Приватний контент і прямі платежі креаторам

## Стан

Реалізація підготовлена в коді. Production-міграція, платіжні Edge Functions і новий вебінтерфейс ще не опубліковані. Реальних списань у перевірках немає. Потрібне окреме погодження застосування SQL, оскільки він змінює правила доступу RLS. Наявні публікації залишаються публічними.

Підтримано UAH: разова покупка поста разом із наступними частинами його ланцюжка; місячна підписка на приватні пости й сторіс автора; або обидва способи доступу. Автор задає окремий публічний опис до 240 символів. Повний текст і медіа не передаються неплатнику. Доступ після публікації незмінний; продовження успадковують його. Для першого приватного продовження потрібна явно задана публічна назва ланцюжка.

Підписка вимагає окремої згоди на автосписання. Скасування залишає доступ до кінця оплаченого періоду. Повернення або спір відкликає доступ; регулярний платіж потрапляє до черги скасування. Повторна підписка до кінця вже оплаченого періоду відхиляється. Новий тариф застосовується до нових замовлень, наявне замовлення зберігає погоджену суму.

Гроші приймає merchant кожного креатора. Комісії, географічна доступність, верифікація бізнесу й підтримка рекурентних платежів залежать від провайдера; безкоштовний хостинг не означає відсутності комісій за еквайринг.

## Порядок публікації після погодження

1. Зберегти резервну копію схеми та перевірити зміни. Для нової бази порядок: `schema.sql` → `maintenance.sql` → `hardening.sql` → `monetization.sql`. На чинній базі застосувати тільки відсутню міграцію `monetization.sql`, одним транзакційним запуском. Це не скрипт багаторазового розгортання.
2. Опублікувати `billing` (JWT), `billing-hook` (без JWT; власна перевірка підписів/cron), `media`, `private-media`, `cleanup`, `account` (JWT). Додати всі імпортовані файли `_shared/`, не тільки entrypoint. Старий `media` також потребує оновлення через спільний облік квоти.
3. `private-media` створює приватний bucket через Storage API при першому дозволеному завантаженні. Якщо bucket помилково публічний, функція відмовляє. Прямі INSERT у `storage.buckets` не потрібні. Cleanup має використовувати нову версію для видалення файлів з обох bucket.
4. Опублікувати вебверсію. Клієнт перевіряє наявність міграції перед приватною публікацією. Окрема функція завантаження захищає від потрапляння приватних файлів у старий публічний endpoint під час переходу.
5. Перевірити двома окремими тестовими акаунтами RLS і Storage на справжньому Supabase. До цього локальні перевірки не вважати підтвердженням production-конфігурації. Перевірити advisories.
6. Платежі залишити вимкненими до тестів підписів, повернення, повторної події, поновлення й скасування з реальним тестовим середовищем кожного провайдера. Перевірка redirect не замінює webhook.

Звичайний відкат вебінтерфейсу не повертає стару схему доступу. Не відкочувати RLS чи видаляти фінансовий журнал за наявності платних публікацій. Для зупинки нових оплат встановити `BILLING_LIVE_ENABLED=false`; скасування й перевірені webhook мають продовжити працювати. Для вже створених Stripe/WayForPay підписок глобальний прапорець сам по собі не вимикає списання у провайдера: потрібне підтверджене скасування кожної підписки.

## Секрети Supabase Edge Functions

Вводити в захищеному сховищі налаштувань, не в чаті, git, браузерних VITE/NEXT_PUBLIC змінних або логах:

| Змінна | Призначення |
| --- | --- |
| `PAYMENT_CREDENTIALS_KEY` | Криптографічно випадковий 32-байтовий ключ у base64 для AES-256-GCM; зберегти резервну копію поза git |
| `STRIPE_SECRET_KEY` | Серверний ключ платформи Connect |
| `STRIPE_WEBHOOK_SECRET` | Секрет підпису webhook connected accounts |
| `BILLING_LIVE_ENABLED` | За замовчуванням false; тільки явне `true` дозволяє нові checkout |
| `MONO_RECURRING_ENABLED` | За замовчуванням false; увімкнути після погодження токенізації банком |
| `BILLING_CRON_SECRET` | Окремий випадковий секрет планувальника |

`SUPABASE_URL` і `SUPABASE_SERVICE_ROLE_KEY` — стандартні серверні змінні Edge Functions. Service-role ніколи не передається клієнту. Без master key інтерфейс не пропонує вводити merchant-секрети. Втрата або заміна master key без перешифрування робить чинні підключення та Mono card tokens непридатними: не ротувати простим перезаписом.

## Підключення провайдерів

**Stripe.** Потрібна активована платформа Connect із доступною країною бізнесу, connected merchant account кожного автора та увімкнені charges/payouts. Onboarding використовує Accounts v2, checkout — Sessions і Billing subscriptions. Direct charges мають `Stripe-Account` підключеного автора. Поточна зафіксована версія API: `2026-10-28.endive`. Webhook: `https://glqsayxjvvnkmhejuqjz.supabase.co/functions/v1/billing-hook?provider=stripe`, події connected accounts: `checkout.session.completed`, `invoice.paid`, `charge.refunded`, `charge.dispute.created`, `customer.subscription.updated`, `customer.subscription.deleted`. Поточний обробник production приймає лише live-події; для sandbox потрібне окреме тестове середовище з явною зміною перевірки режиму, не надсилати штучні події у production. Одноразовий success URL не відкриває доступ.

**WayForPay.** Кожен автор має merchantAccount, secret key та merchantPassword для regularApi. Збереження шифрує секрети і залишає підключення pending. Адміністратор активує конкретний `account_id` через service-only `billing_backend('account_activate', ...)` лише після перевірки володіння й callback. Адреса callback формується сервером для конкретного order UUID. Перевіряються HMAC-MD5, merchant, замовлення, сума, валюта й replay key з підписаних полів. Для підписки додатково STATUS перевіряє місячний режим і ціну через merchant API: поля регулярного платежу у браузерній формі не покриваються Purchase-підписом. Невідповідний план скасовується, доступ не надається. REMOVE та STATUS використовують код успіху **4100**, відмінний від purchase-кодів. Очікувана ще не створена регулярка або невідома відповідь потребує звірки; не позначати скасування успішним без підтвердження.

**Monobank.** Кожному креатору потрібен merchant X-Token еквайрингу. Підключення перевіряє merchant/details і кешує merchant/pubkey, залишаючи pending до тесту callback. Для регулярних оплат потрібна окрема активація токенізації банком, прапорець у підключенні та серверний `MONO_RECURRING_ENABLED=true`. Перша оплата зберігає cardToken лише для підписки; наступні — merchant-initiated wallet/payment. Дані картки не вводяться в LelekaThoughts. Webhook перевіряє raw-body ECDSA за кешованим ключем, потім звіряє invoice/status, reference, ccy та суму. При зміні merchant pubkey оператор отримує новий ключ авторизованим запитом і оновлює `billing_backend('account_pubkey', {account_id,pubkey})` через service role. Не завантажувати pubkey за кожним неавторизованим callback.

Офіційні джерела: [Stripe Connect](https://docs.stripe.com/connect/accounts-v2), [WayForPay STATUS](https://wiki.wayforpay.com/view/852526), [WayForPay REMOVE](https://wiki.wayforpay.com/view/852521), [Monobank acquiring](https://api.monobank.ua/docs/acquiring.html).

## Планувальник, звірка та видалення

Налаштувати раз на хвилину POST `.../functions/v1/billing-hook?renew=1` із заголовком `x-billing-cron`, секрет якого береться зі сховища секретів планувальника. Не зберігати його літералом у cron SQL чи git. За один запуск обробляється до 10 скасувань і до 10 Mono поновлень. Скасування обробляються навіть при вимкнених нових оплатах. Stripe і WayForPay поновлюють самі; запускати додаткові ручні списання для них не можна.

SQL claims блокують рядок і використовують SKIP LOCKED; повторні події не продовжують оплачений період двічі. Mono timeout або невідомий результат переходить у стан звірки без повторного списання. Оператор перевіряє invoice/provider перед будь-якою зміною стану. Не скидати processing/unknown для автоматичної повторної спроби. Pending checkout не перемикається на іншого провайдера до звірки. Для простроченого невикористаного checkout також потрібна перевірка стану провайдера, а не повторний платіж навмання.

Блокування та призупинення ставлять пов’язані підписки в чергу скасування. Видалення акаунта спочатку зупиняє підписки; якщо провайдер не підтверджує, видалення завершується після звірки й повторної спроби. Профіль/контент/медіа видаляються; обмежений серверний фінансовий журнал і зашифровані merchant-дані зберігаються для повернень та пізніх callback. Окрему політику строку зберігання слід визначити перед реальним платним запуском.

## Межі захисту й перевірок

Прев’ю зберігаються окремо, не є обрізаним приватним текстом. Дозвіл надає база, а не клієнтський paywall. Приватні файли мають signed URL на 60 секунд; уже виданий URL може діяти до завершення цих 60 секунд після відкликання. Авторизований покупець може зберегти отриманий контент — це не DRM.

Клієнтський маркер `paid-content/1` — тільки сумісність старих редакторів; він не замінює оплату. Старі APK не отримують приватні оригінали й потребують окремого оновлення для інтерфейсу покупок. Цей патч стосується вебверсії та backend.

Локально: `node --import tsx --test scripts/billing-database.test.ts scripts/billing-payments.test.ts scripts/security-regression.test.ts`. PGlite виконує реальний SQL/RLS на локальних ролях із auth/storage stubs; він одноз’єднаннєвий і не доводить поведінку конкурентних Supabase-запитів. Провайдери перевіряються моками з криптографічними підписами. Браузерний прогін використовує локальні fixture API без production-записів. Окремо перевіряються Deno typecheck та Next production build.
